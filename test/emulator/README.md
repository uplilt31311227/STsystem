# 情境測試（Firebase Emulator）

用完整假資料在**本機 Firebase Emulator** 上驗證四類情境。正式 Firestore 全程不會被碰到。

## 為什麼一定要用 Emulator

2026-07-30 曾發生 `test/v2-rules-matrix.mjs` 直接打正式 Firestore、寫入 16 筆 `zz_test_`
測試文件的事故（見 `docs/ISSUES_LOG.md`），其中 1 筆 `operationLogs` 依規則設計永久不可刪。
這套測試從結構上杜絕同類事故：

- `emu-client.mjs` 的 host 寫死 `127.0.0.1`、專案寫死 `demo-stsystem`（`demo-` 前綴會讓
  Firebase CLI 進入離線模式，不可能連到真實專案）。
- 每次連線前先探測對端確實是 Emulator，失敗就中止，不 fallback、不讀任何憑證檔。
- 全程不需要、也不會讀取任何正式環境的憑證。

## 用法

```bash
# 終端機 A：啟動 emulator（持續執行）
npm run emu

# 終端機 B：跑全部情境測試
npm run test:scenarios

# 只想種一份假資料、用 Emulator UI 手動點（http://127.0.0.1:4000/firestore）
npm run seed
```

需求：Java（Firestore Emulator 依賴）與 `npm install` 安裝的 `firebase-tools`。

## 假資料

`test/fixtures/` 下的產生器一律使用固定 seed，同一份程式每次產生完全相同的資料，
測試失敗時可重現。日期一律寫死，不會隨執行日期漂移。

兩所學校（`demo-alpha` 9 班 / `demo-beta` 6 班），各含：

- 22 位教師：主任、教學組長、一般教師、3 位未綁定 email、2 位不任課的行政人員
- 兩個學期的完整課表（目前學期 `115-1`、歷史學期 `114-2`），排課保證無教師衝堂
- 22 筆已成立紀錄：8 種假別（中英文代碼混用）＋一般調課／自行調課
- 6 筆待審請求：代課單簽、調課雙簽（待同意／待核准）、多重調課部分同意、已駁回、
  alpha 期舊格式（`status='pending'`、無 `requestType`）
- 操作日誌，欄位形狀對齊 `firestore.rules` 的白名單

另有平台管理者與「不屬於任何學校」的外部帳號，供權限邊界測試。

## 輸出中的「系統既有行為」

報告最後會列出測試過程確認的既有行為（例如課表匯入不做衝堂偵測、同名教師會被合併）。
這些**不是測試失敗**——是測到了、且系統目前確實如此，列出來供判斷是否需要處理。
